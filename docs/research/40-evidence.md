- One role-based `e2e.mjs` per template that every variant passes, including authorization and no-JS behaviour.
- Declare each stack's component kit. Report JS plus CSS together.
- Publish runs: 5 × 60 s, median of runs, floors max(1 ms, 5%). No composite score or Lighthouse headline.
- A "where weft loses" table is mandatory, starting from 389/416 rps against Solid 445/498 and Next 720/802.
- **Gate for any public claim:** pre-registration, holdout, critic sign-off, canary and query assertions, Caddy, open-loop, parity e2e, agent evals n≥3.

### 3. New probes for evals/apps

- `db.canary`: write a random row before each sample; the page must render it or the sample fails. Label pages uncached, cached-hit or static shell.
- `db.queries`, `db.rowsRead`: per-request counts from `pg_stat_statements` deltas.
- `db.roundTrips`: (TTFB at 40 ms − TTFB at 2 ms) ÷ 38 ms.
- `server.ttfb.p50/p95/p99`, `server.flush.head` (`</head>` byte), `server.flush.lcp`, `server.ttlb` (TTLB on small pages only).
- `server.open`: fixed arrival rates from scheduled send time, pushing concurrency past the pool, 60 s after warm-up. Report highest rate with p99 TTFB under 500 ms and zero errors. Label same-host runs.
- `server.cache`: shared, per-user, always-unique rows; cold, warm, and 100 concurrent requests after invalidation, counting queries.
- `flow.nav.url/.paint/.data`: real click to URL, first new paint, named element. MutationObserver plus rAF. Cold, hovered, back, deferred slow panel. Count prefetch invocations and bytes.
- `flow.interaction.worst/.p75`: trusted input (`dispatchEvent` is untrusted, evals/apps/lib/measure.mjs:79; confirm CDP is), 4× CPU, 8 ms floor. Never labelled INP.
- `flow.interaction.streaming`: time to first successful interaction during the 2 s Boundary.
- `flow.mutate.optimistic/.confirmed/.consistent/.requests/.rowsRequeried`.
- `race.*`, pass/fail on final DOM equals DB: double submit, 5 toggles with shuffled replies, failure rollback, pending-row action, navigate during mutation, invalidate during read, two tabs, stale tab after deploy. Failure outranks any ms win.
- `bytes.wire.html`, `bytes.data`: split markup, data, CSS, raw and compressed, at 50/500/5000 rows.
- `css.head`: head plus shell br bytes. Axis: links, 48 KB, 256 KB, critical plus deferred; cold and repeat.
- `template.green`: human steps and time from create to passing e2e, all stacks.
- `agent.*`: same plain one-line brief per site, stock scaffold on each stack (real AGENTS.md intact), no optimisation words. Score pass@1, bench metrics, turns, errors, tokens. n=3 for todo and admin; landing n=1 labelled smoke. Weft-with-template is a separate row. Publish the naive-to-expert gap per stack; "optimal by default" means near zero.

## Findings

### methodology

evals/apps cannot yet benchmark a database-driven page. Its Lemonstand note says no page reads the DB while rendering, and it has no DB lifecycle, no first-byte timing, no interaction or navigation passes, no latency model and no proof a page hit the DB. It also records only full-body latency from a closed-loop client.

Priority order:
- First, 'prove the DB was hit' plus the seed and reset lifecycle.
- Second, first-byte and flush timing with an open-loop load generator.
- Third, Toxiproxy latency tiers and a query log.
- Fourth, scripted flows for INP, soft navigation and mutation.

Three weft behaviours should show up as real gaps once these exist:
- The first byte waits for all `load`s (server.tsx:249), and they run serially (server.tsx:624-630).
- Soft navigation awaits deferred data (server.tsx:370-374).
- There is no query batching or Server-Timing.

Verified means I read the code or fetched the page. Items marked [inferred] are my reasoning, and nothing was run. The Mac was at load 85, and this task is read-only. Chrome 151 soft-nav shipping is confirmed only as an approved Intent to Ship with an estimated milestone, not as a stable release. TechEmpower's sunset comes from secondary sources, and its results page reportedly no longer serves content, so I could not read it. Published SSR benchmarks with a real DB and all three of Next, Solid and a third stack were not found, so this suite would be new territory.

Verified docs and code; the Next-specific failure on our apps is [inferred].
- [high / overstated] setup is skipped on reuse, so file DB state from a previous run, including mutations, carries over and an external DB is not reseeded. buildKey covers the setup command and files in the variant folder, but not seed data outside it. Nothing resets between samples. Evidence: evals/apps/lib/build.mjs:119,133-139,143,154; evals/apps/lib/app.mjs:52; evals/apps/lemonstand/app.json:3. - [high / confirmed] loadPass records only full-response time, so TTFB and first flush are invisible, and streaming and blocking pages look identical at p95. Cloudflare's write-up shows the mirror-image trap: TTFB alone misleads when one mode buffers and another streams early. So both are needed. bench's real-trace LCP phases include TTFB, but only on an unloaded server. Evidence: evals/apps/lib/measure.mjs:115-122; evals/apps/lib/stats.mjs:42-44; https://blog.cloudflare.com/unpacking-cloudflare-workers-cpu-performance-benchmarks. Do: Record per request: first byte, first byte containing `</head>` (CSS and preloads known), byte of the LCP element, last byte, and bytes and timing per flush. Add metrics `server.ttfb.p50/p95/p99`, `server.flush.lcp`, `server.ttlb`. Keep real TTLB from small pages only, so it does not measure bandwidth.
- [high / overstated] The closed-loop 10-connection load hides queueing. Pool wait is bounded by client concurrency, not by the 2 s window: at one query per request, 10 clients cannot exceed a 10-connection pool. An open-loop pass needs arrival rates that push concurrency past the pool, not just more seconds. Evidence: evals/apps/lib/measure.mjs:111-128; evals/apps/bench.mjs:119-120; packages/start/src/db/postgres.ts:24; https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/; https://blog.platformatic.dev/ssr-framework-benchmarks-v2-corrected-results. Do: Add an open-loop pass (k6 constant-arrival-rate, or a generator scoring against scheduled send time) on a separate machine, stepping arrival rate: 25/50/75/100% of each stack's closed-loop peak plus fixed absolute rates. Report the highest rate with p99 TTFB under 500 ms and zero errors, 60 s minimum after warm-up. Fix pool size equal across stacks and record it. Keep the current pass as the quick after-every-tweak check. yuna-mbp as client with this Mac as server is an option, but it needs a quiet Mac.
- [high / overstated] Weft sends nothing until awaited loads and non-Boundary queries finish, and awaited nested loaders run in series. Deferred promise fields stream, but only after that. Next ships a shell first only when uncached work sits behind Suspense. Whether weft loses is unmeasured. Evidence: packages/start/src/server.tsx:249,256,285,624-630; docs/PLAN.md:1325; https://nextjs.org/docs/app/getting-started/caching. Do: Benchmark two authorings per stack: 'as an agent writes it' (naive awaits, no tuning) and 'expert'. Publish the gap as the primary agent metric: optimal-by-default means the gap is about zero. Test a page with 3 nested layouts each doing a 20 ms query. Candidate weft tweaks [inferred]: flush head and CSS before loaders once redirect risk is settled, and run non-guard loaders concurrently. The code is verified; the loss is not measured.
- [high / confirmed] DB latency must be real network distance, not a sleep. A `setTimeout` (Platformatic used a random 1-5 ms delay) models no sockets, pool wait, TLS, serialization or round-trip count. N+1 is free under one sleep but ruinous under per-query RTT. Developerway's 100 ms/1 s API delays are good for showing UX shape but not throughput. ### data-layer

Audit of Weft's full-stack data path at /Users/ravonus/dev/weft-wt/benchmarks (packages/start, packages/weft).

How it was checked: every finding comes from reading the code. I executed nothing, because this worktree has no node_modules and the machine load was 77. Each sequence is a traced code path, not a reproduction. Claims about other stacks and driver behaviour are marked as inference.

Root cause of the worst races: the client cache has no ordering. `setBase` (data.ts:523) accepts whatever response arrives last, and in-flight dedupe ignores invalidation. Findings 1 and 2 share that root, and a small per-entry generation counter fixes most of it. Every race finding below lacks a test because the fake transport uses one fixed latency, so responses can never reorder. Using `runtime.transport` with hand-resolved deferreds (data.ts:657 gives it priority) would make all of them deterministic tests.

Already acknowledged in docs/research/27-server-functions.md:284-287: route data is a second request, no stale-while-revalidate, no eviction, no `query.batch`. Those are known gaps. The findings add the concrete cost or a race the doc does not mention.

What held up:
- Hydration fetches nothing on the normal path (data.browser.test.mjs:39).
- Shared-cache versions are read before `run`, so a bump during a run rejects the stored value (exec.ts:172-174).
- Stream ordering is safe: `$wb` runs inline and tolerates a missing marker, and hydration cannot overtake it because the entry is deferred.
- Optimistic layers roll back per call (data.test.tsx:75).
- A navigation's data fetch is aborted by the next `go()`, so a stale `/_weft/data` response cannot land.

Benchmark gap: evals/apps and evals/compare have no load test, mutation-race or pool scenario (grep of both READMEs). Findings 1-4, 11 and 12 therefore need new scenarios: an open-loop load generator against a Postgres-backed page, and injected latency jitter on mutation responses.

### css

Today every build puts all of a page's CSS in the head, up to 256 KB of text (packages/start/src/inline.mjs:5, server.tsx:603-611). There is no first-paint vs later split. 'Later' CSS exists only for lazy loads and client navigation, through Vite's preload helper.

Verified by measurement on existing builds, nothing rebuilt:
- Applying the 256 KB limit to the current site build gives the /docs head 170 KB of CSS, or 26 KB at the server's brotli q5. That exceeds the roughly 14 KB first window, so inlining at this size does not remove the round trip it was meant to save. It only moves it, and repeat views lose caching.
- On the dashboard (19.8 KB br11, 22.5 KB br5), tokens, at-rules and rules matching the loaded DOM come to 12.8-13.4 KB br, or 14.4-14.8 KB with state variants. The unmatched rules compress to about 12 KB on their own. The dashboard's CSS is 158 KB raw against 5.4 KB hand-written.

Measurement gap: evals/apps/results.json (commit 1174811) predates default inlining (1691ad5), and the dashboard is client-rendered, so no benchmark covers the current behaviour.

Recommended strategy:
1. Inline all CSS only when head plus shell fit about 12 KB br.
2. Otherwise inline a per-page critical set computed from the server HTML with the existing purge logic.
3. Load the rest as an immutable, non-blocking link.
4. Emit one fixed @layer order statement first.

Expected (modelled with TCP slow start at 150 ms RTT, not measured): one fewer round trip, about 150 ms on a cold first paint, for pages with 20 KB+ of CSS, and 50% less CSS in each document. Lemonstand-sized pages stay fully inline and do not change.

Ordering and race risks, found by reading code and not reproduced: islands in streamed Boundaries get no head CSS, the `app` layer's position depends on arrival order, static routes may lose warp CSS from tarball installs, and strict CSP leaves pages unstyled.

Next.js defaults to links and marks inlining experimental (https://nextjs.org/docs/app/api-reference/config/next-config-js/inlineCss). Astro's `auto` inlines only under about 4 kB (https://github.com/withastro/astro/commit/8a5b0c1f3a4be6bb62db66ec70144109ff5b4c59). SolidStart uses links, with FOUC and lazy CSS as open design discussions (https://github-redirect.dependabot.com/solidjs/solid-start/discussions/1458), though that comes from RC-era discussions, not current docs.

### warp-custom

Warp handles "same look, different hue" well, but real customisation is harder than it should be. The checked path (warp()) gets stricter as the look moves away from the default, and the unchecked path (raw `--warp-*` in app CSS) passes silently.

**Shortest correct path today**
- Warm editorial: `warp({ dials: { expression: 'vivid' }, fonts, tokens: { '--warp-ref-neutral-h': '70', '--warp-ref-neutral-c': '0.03' } })`. It passes the contrast gate, but it uses a private token.
- Brutalist: `radius: 'sharp'` stops at 2px, so 0 needs `tokens`. Black borders and hard shadows need component rules, and those hit D001.
- Match this brand: the seed does not land the brand colour. The agent must hand-write `light-dark()` pairs for solid and hover.

**Comparison (from their docs)**
- shadcn is token pairs plus owned code: override variables under `:root` and `.dark`, then map them with `@theme inline`.

- Warp's contrast guarantee and dials are stronger than either. It lacks an exact-brand path, a gray/neutral option, per-theme overrides and any code ownership.

### agent-ergonomics

Verdict: at the client-reactivity level the natural code comes out fast. Above that level (Warp pages, data, images, the agent loop) it does not yet.

**What the framework computes for the agent**
- Reactive lowering, live props and keyed lists.
- Burst batching. v4: "Bursts merge into one flush for free".
- Islands and their load timing. Lemonstand: 5 islands, all visible or interaction, 0 diagnostics in .weft/hydration.json.
- CSS inlining, font subsetting and metric fallbacks once the text plugin is installed.
- Request-level query dedupe (exec.ts:5).
- Link warm-up (run.tsx:71).

**What the agent must still get right**
- Cache tags and invalidation, and optimistic updates.
- Load-versus-Boundary placement.
- Pagination, indexes and N+1 avoidance.
- Adding the media and text plugins.
- Per-entry reads (W017) and stable item identity (W014).
- Keeping closures out of route bodies.
- Async races.

**Top gap.** Warp, the default UI, defeats partial hydration, and no benchmark covers that. evals/compare and the dashboard app are client-rendered, and Lemonstand has no Warp dependency.

**How I checked**
- Verified means I read the code, or ran the repo's own solve() and compiler.transform from packages/weft on probe files in the scratchpad.
- That probe left @weft-js/warp-icons unresolved. The per-component reasons for Layout, Type, Card and Button don't depend on icons. I ignored the icon-related 'load' entries as a likely artifact.
- I did not run a build or a browser, so no byte costs were measured.
- Items marked inferred are design judgement.

**Ranked leverage of what the framework should decide**
1. Make Warp static by default.
2. Hoist closures, and report every whole-route fallback.
3. Write AGENTS.md and the MCP config at scaffold time.
4. Print a per-route perf report from `weft build`.
5. Derive tags from touched tables.
6. Have the DB layer guard indexes, limits and N+1.
7. Lower safe fixes in the compiler.
8. Include the image and font pipelines by default.
9. Infer data placement.
10. Add the missing race and `let` diagnostics.
