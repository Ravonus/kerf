# 17 — Phase 1 agent layer: config, check, tasks, AGENTS.md, MCP

Research date: 2026-10-29. Numbers marked **(measured)** were run for this doc on an M4 Max (1-minute load 6–9,
other agent sessions running) with Node 22.22.1, TypeScript 5.9.3, Zod 4.6.7 and Vitest 5.0.5, against the
compiler from research 16 (`crates/weft-compiler` at `ab663fa`).

The CLI uses the compiler only through `@weft-js/core/compiler`'s `transform()` and its diagnostics, never through anything
specific to the code generator. So PLAN §3.6's 2026-10-29 decision (weft owns its back end, and the spike's
Solid crate leaves the build once weft's own back end passes the same gates) changes nothing here. The agent docs never say what
weft's output is generated by.

**The question:** PLAN §9's Phase 1 row lists "`weft.config.ts` (with reserved `plugins`/`slots` keys and P100–P120)
+ `weft tasks --json` + P-codes, generated AGENTS.md, `weft check --json`, MCP `docs`/`check`/`tasks`". What do these
look like when built, and what does PLAN leave unspecified?

**What was built:** [`packages/cli`](../../packages/cli) (`@weft-js/cli`, bin `weft`). It has 39 tests, and every command
runs on [`evals/reference-v3/weft`](../../evals/reference-v3/weft) and on planted copies of it. The compiler is used
only through `@weft-js/core/compiler`'s `transform()`. The README covers usage and the diagnostic shape.

---

## TL;DR

1. **All five Phase 1 pieces work on the v3 reference app.** `weft check` finds nothing in the reference. With the
   v3 spread habit planted, it reports one W014 **error** that points at the keyed list two files away. The compiler
   alone reports that case only as a warning.
2. **`weft check` is fast enough without a cache.** On research 16's 1k-component corpus it takes **47–74 ms**
   in-process, or **0.25–0.31 s** wall time including Node startup **(measured)**. The budget is ≤ 3 s cold and ≤ 0.5 s
   warm. The project view parses only when a W014 warning exists; parsing every file costs ~270 ms per 1k files.
3. **AGENTS.md is generated from what the installed weft actually does: 4.6 KB of the 8 KB budget.** Each W-code has an
   example, and the CLI runs the installed compiler over the examples. The diagnostics table lists only codes that the
   compiler reports today: W001, W005, W006, W010, W013, W014 and W015. The API section lists the installed exports:
   against `ab663fa` it names `resource`, `<Boundary>` and `defineState` as not shipped yet. Against the
   `phase1-define-state` branch (70c03ce) it lists them, with `hydrate`, `@weft-js/core/ssr`'s `renderToString` and
   `renderToStringAsync`, and an async rule (4.99 KB). That keeps the doc from listing APIs that don't exist,
   which is the failure an agent would hit first.
4. **PLAN gaps worth fixing** (§2 below):
   - the exact diagnostic JSON;
   - a home for config-validation codes (P100–P120 is full);
   - Phase 1's plugin-entry shape;
   - §7 vs §9 disagreeing on the MCP tool list;
   - where the CLI and `@weft-js/core/config` live.

## 1. What each piece does

| Piece | Behaviour | Tests |
|---|---|---|
| `weft.config.ts` | `defineConfig` with types (`src/config.d.ts`). Loaded with Node's sync module hooks: TypeScript transpiles it (non-erasable syntax works) and `require(esm)` loads it, so loading also works inside vitest's vm. `@weft-js/core/config` falls back to the CLI's module. Each load gets a fresh module id, so `weft mcp` sees config edits. Zod validates the schema: unknown keys and wrong types are P007, with the path | 7 |
| P-codes | P003 (built-in name or duplicate command), P004 (no `description`/`sideEffects`), P007, P008, P009, P100, P116, plus P002 (`package.json` script not `weft …`) and P120 (`@weft/plugin-*` imported in `vite.config.*`). Each is located at the task or plugin name | 9 |
| Slots | Research 13 §2.2's table and binding rules, from config data. A default binding is reported by name (`weft:default:memory`), never silently. Two providers are P100, whatever the array order (tested both orders). `slots: {}` picks the winner | 3 |
| `weft check --json` | Every `.tsx`/`.jsx` file outside `node_modules`, `dist`, `.weft` and `scope.forbid`. Each file is compiled with `checkOnly`, and byte offsets are converted to UTF-16 spans and offsets (tested with `é` and `🎉`). Fixes carry edits. The output has a `slots` block and exit codes 0/1/2 | 8 |
| Project view | Cross-file W014: from the flagged `.map`, it finds the box (`box.value = …`) and follows it through JSX props, `derived` locals and further components to a JSX `.map`. A hit becomes an **error** with `related` locations and `project: true`. If no list is found, the warning stays | 3 |
| `weft tasks --json` | Built-ins (`available: false` for the ones PLAN names but this build doesn't ship) plus project tasks. Args are JSON Schema, and Zod schemas are converted with `z.toJSONSchema`. The output also has side effects, environments, scope and the task P-codes | 3 |
| Docs and AGENTS.md | Topics: `rules`, `props`, `lists`, `async` (`resource`, `<Boundary>`, `@weft-js/core/ssr`, `hydrate`), `testing`, `config`, plus the generated `diagnostics`, `commands` and `agents`. Every code has a page with its status in the installed weft. AGENTS.md's Commands section comes from `weft tasks`, and `agents-md --check` fails when the file is stale | 10 |
| `weft mcp` | Newline-delimited JSON-RPC 2.0 on stdio, written directly with no SDK dependency. It negotiates the protocol version, serves `tools/list` and `tools/call` for `docs`, `check` and `tasks` (JSON as text and as `structuredContent`), and returns JSON-RPC errors for unknown methods and tools | 3 |
| CLI | JSON on stdout, human text on stderr, `{ ok: false, error: { code } }` on usage errors | 5 |

On the reference app, `weft check` takes 26 ms for 6 files, and all 39 tests run in 2.2 s **(measured)**.

### Cross-file W014: what it follows and what it misses

It follows:
- `<C prop={box.value}>`, `<C prop={box}>` and `<C prop={derivedOfBox.value}>`;
- destructured props, `props.x`, and `derived`/`state.linked` locals;
- further JSX props, through any number of components;
- imports from relative paths, `index` files and the same file.

It misses:
- boxes passed through `context`, module-level stores, function calls or spreads (`<C {...p}>`);
- re-exports (`export { X } from`);
- path aliases.

The parse is syntax-only (TypeScript's parser, no checker). The compiler cannot report this case itself, because a
single-file compile can't see the consuming component.

When this moves into Rust, the compiler can emit a per-file summary ("box X flows into prop P of import I"; "prop P
reaches a JSX `.map`"), and `weft check` would join the summaries without parsing anything.

## 2. Proposed PLAN edits

1. **§3.5, add the JSON shape** after the catalog table. Proposed text:

   > Every diagnostic, from any command, is
   > `{ code, severity, owner, file, span: [line, col, endLine, endCol], offset: [start, end], why, fix: { text, safe?, edits?: [{ file, span, offset, text }] }, related?, project?, docs }`.
   > Lines and columns are 1-based, columns and offsets in UTF-16 units. `owner` is `core`, `slot:<id>` or a plugin
   > name (research 13 §2.8).

   Also ask the compiler to emit UTF-16 offsets. Today it emits UTF-8 byte offsets and the CLI converts them, and every
   other consumer (the Vite plugin, an editor) would have to convert them too.
2. **§3.5, W014 row.** Change "(error in-file, warning when the list leaves the file)" to: "(error in-file; across
   files, `weft check`'s project view makes it an error when the box reaches a keyed list, research 17)".
3. **§7b P-codes, add P007–P009.** Config validation needs codes, and P100–P120 are all assigned. Proposed:
   - **P007:** weft.config fails to load or fails the schema (Zod path given);
   - **P008:** `slots`, or a plugin's `provides`, names a slot weft doesn't define;
   - **P009:** `slots` picks a winner that isn't in `plugins` or doesn't provide that slot.

   These are implemented now and marked `proposed` in the catalog.
4. **§7c / research 13 §4.2, Phase 1 plugin entries.** P100 needs to know what an entry provides, but Phase 1 has no
   `definePlugin`. Proposed: in Phase 1, a `plugins` entry is data, `{ name, version?, provides?: (SlotId | { slot,
   key })[] }`, validated but never executed. When `definePlugin` lands, a plugin instance carries its frozen
   `contribute()` result, and the same checks read `provides` from it.
5. **§7b manifest, add `check: { include?, exclude? }`.** It sets which files `weft check` compiles. The default is
   `**/*.{tsx,jsx}` minus `scope.forbid`, matching the Vite plugin's filter.
6. **§7, MCP tool list.** §7 says "`docs`, `check`/`fix`, `catalog`"; §9 Phase 1 says "`docs`/`check`/`tasks`".
   Proposed text for §7: "MCP server (`weft mcp`): `docs`, `check`, `tasks` (Phase 1); `fix` and `catalog` with the
   plugin API (Phase 2); later `inspect`, `scaffold`." Also: "Each tool returns the same JSON as the CLI's `--json`."
7. **§7, AGENTS.md.** Add: "Generated by `weft agents-md` from the installed weft. It lists only the diagnostics that
   version reports (each catalog code has an example the compiler is run on) and the exports it has.
   `weft agents-md --check` runs in CI." The generated file is 4.6 KB, so the 8 KB budget leaves room for one section
   per plugin.
8. **§3.2, the one-screen example** uses `Stack`, `Badge` and `Text` from warp, which doesn't exist until Phase 2.
   The generated AGENTS.md uses plain elements. Proposed: §3.2 gets the plain-element version until warp tier 1
   ships. It also adds two rules agents need first: `state.linked` (W005) and stable list items (W014).
9. **§8 packages: where the CLI and `@weft-js/core/config` live.** §8 puts the CLI and `@weft-js/core/config` in `packages/weft`. This
   build is a separate `packages/cli` (`@weft-js/cli`) so it didn't collide with parallel work on `packages/weft`.
   Proposed: keep the CLI separate, since it depends on TypeScript (~23 MB) and Zod, and the runtime shouldn't. Then
   `packages/weft` gains a two-line `@weft-js/core/config` subpath that re-exports `@weft-js/cli/config`. The loader already
   prefers a real `@weft-js/core/config` when one resolves.
10. **§3.6 `weft check`, the tsc half.** This build doesn't run `tsc`, so W007 (TS2540) and W008 (box/value mismatch)
    can't be reported yet. Next step: run `tsc --noEmit` (TS 7 is `typescript@7.0.2` on npm) in parallel with the
    compiler pass, map the codes, and add it to the probe so AGENTS.md picks up W007/W008 automatically.
11. **§3.5, two catalog notes.**
    - The compiler reports a state-dependent early `return` in a component body as **W001**, not **W040** (the W040
      example produces W001). Either map it to W040 in the compiler or merge the rows.
    - W001's edit is marked unsafe, so AGENTS.md shows it as "suggested edit", not "autofix". §3.5 says "autofix where
      mechanical", and that matches.
12. **`@weft-js/core/dom` and `@weft-js/core/ssr` export compiler helpers** (`insert`, `template`, `ssrHydrationKey`, …) next to
    `render`, `hydrate`, `renderToString` and `renderToStringAsync`. AGENTS.md
    says "never import them", but an agent that lists the exports will see them. Proposed for packages/weft: put the
    helpers on `weft/dom/internal` and `weft/ssr/internal` (or one `weft/runtime`), and keep the public subpaths to
    the entry points. weft's own back end (PLAN §3.6) defines and versions that helper set anyway, so this is the
    moment to make the split. Until then, `agents-md` lists only the entry points.
13. **`weft run`.** Until `weft run` ships, `weft tasks` gives each project task's own command (`run`) as `command`.
    PLAN should say how args reach the command: proposed `weft run <name> --json '<args>'`, validated against the
    task's schema and passed as JSON on stdin.

## 3. Not done here, and why

- **P001, P005, P006** need a diff against the base branch, which is the test gate's job (Phase 1b). Their catalog
  entries are reserved.
- **`.weft/slots/` generation** (research 13 §4.2, Phase 1). Nothing consumes the slot modules until Phase 2, and the
  `slots` block in `weft check` already reports the bindings.
- **Content-hash cache.** At 47–74 ms per 1k files it isn't needed yet. Revisit when the tsc pass lands.
- **The Phase 1 exit check itself** (agent pass@1 on weft beats React and Solid). The pieces it needs from this layer
  are in place: a generated AGENTS.md for the weft starter and `weft check --json` for the agent's loop. The run is
  research 16 §6.10's v3 eval with a weft column, still to do.
